# AETHERIS: інструкції для агентів

Онлайн 2D космічна стратегія в реальному часі. Сервер C# (ASP.NET Core), PostgreSQL 17, клієнт React + TypeScript (Vite, PixiJS для гри). Автор українськомовний: спілкування, README і документація українською, код і коментарі в коді англійською.

## Обов'язково прочитай перед роботою
1. `documentation/tech/08-pravyla-kodu-dlia-ahentiv.md`: жорсткі правила коду (нуль хардкоду, сутності гри як дані, іменування `_id` / `_ids`, 3D-координати, модульний моноліт, транзакції, секрети).
2. Файл поточної задачі в `documentation/tasks/` (критерії приймання; у кінці дописуй розділ «Результат виконання»).
3. Якщо задача чіпає інтерфейс (будь-яка сторінка клієнта, включно з адмінкою): `documentation/ui-art/05-yedynyi-styl-interfeisu.md`, єдиний обов'язковий стиль. Лише токени з `client/src/styles/tokens.css` і готові компоненти, жодних кольорів, шрифтів, відступів чи радіусів «від себе».
4. Пов'язані документи, названі в шапці задачі (`documentation/game-design/`, `tech/`, `ui-art/`).

## Виконання задачі (абсолютне правило автора, ✅ 31.10.2026)
Це правило стосується АБСОЛЮТНО ВСІХ задач без винятку: сервер, клієнт, дані, міграції, адмінка, тести, документи, дизайн.
1. Задача виконується ВСЯ, від початку до кінця, без помилок, оптимально й якісно. Стану «частину зроблено» немає: не оголошуй задачу виконаною, доки не виконано всі критерії приймання й усе, що задача описує (для задач з макетом ще й усі елементи макета), і доки не виконано вимоги оптимізації.
2. Оптимізація обов'язкова частина кожної задачі, будь-якого типу: сервер без N+1 (пакетні запити, `AsNoTracking`, потрібні індекси), без зайвих запитів до БД, мережі й перерахунків, без опитування по таймеру там, де є подія; клієнт без зайвих запитів і перемальовувань (стабільні окремі блоки, наприклад шапка, меню й футер не перемальовуються разом зі сторінкою; ліниве завантаження сторінок); дані й міграції без зайвих блокувань і повних перебору таблиць.
3. Після виконання питань автору не лишається. Питання або вирішується одразу (ухвали найкраще рішення за документами й правилами та запиши його як рішення), або, якщо без автора ніяк (правило чи механіка гри), виноситься в окремий файл `documentation/tasks/<номер>-pytannia.md`, а задачу виконуй за обґрунтованим варіантом за замовчуванням.
4. Файл задачі лишається чистим: опис, критерії, рішення й «Результат виконання» (що зроблено, тести, результати команд). У ньому немає розділів «Питання до автора», «Відкрито», «Зауваження», «Припущення», «Що не перевірено» тощо: усе це йде в `<номер>-pytannia.md`. Результат лише правдивий: нічого не стверджуй, чого не перевірив; що агент не може перевірити (ручна перевірка в Chrome, CI), теж іде в `<номер>-pytannia.md`.
5. Якщо не вистачає ресурсів (токенів, часу), збережи стан і передай далі точний перелік лишку; не оголошуй задачу виконаною.

## Основне
- Баланс-числа в документах це стартові значення, їх потім підлаштовує симулятор; не питай автора про цифри балансу, питай лише про правила й механіки.
- Задачі зі статусом «чернетка» не виконувати.
- Нічого не запускай у Docker до релізу v0.1. Локально: `dotnet run --project server/src/Aetheris.Host` та `npm run dev` у `client/` (.NET лежить у `~/.dotnet`).
- Тести тільки на базі `aetheris_test`; рядок підключення не потрапляє в репозиторій і не виводиться у відповіді.
- Не змінюй `documentation/`, окрім оновлення статусу й результату своєї задачі.
- Перед завершенням: `dotnet build -c Release`, `dotnet test -c Release`, `dotnet format --verify-no-changes --no-restore`, у `client/` lint і build.
- Коміть у `main` зрозумілими повідомленнями; `git push` робить автор.
