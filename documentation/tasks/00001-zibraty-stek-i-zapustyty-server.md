# Задача 00001 — Зібрати початковий стек і запустити сервер

> **Статус:** не розпочата (створено 25.10.2026)
> **Етап:** підготовка до етапу 1 (production/01)
> **Документи:** [tech/01 Архітектура](../tech/01-arkhitektura.md), [tech/02 Стек](../tech/02-tekhnolohichnyi-stek.md), [tech/03 Модель даних](../tech/03-model-danykh.md), [tech/04 API](../tech/04-api.md), [tech/06 Тестування](../tech/06-testuvannia-ta-symuliatory.md), [tech/07 Планувальник](../tech/07-planuvalnyk-podii.md)

## 1. Мета
Порожній, але **робочий каркас сервера**: проєкт збирається, підключається до PostgreSQL, запускається однією командою, відповідає на перевірочний запит, має тести й CI. Ігрової логіки ще немає.

## 2. Що входить

### 2.1. Структура рішення (модульний моноліт ✅)
- Рішення `.NET` (остання LTS) з проєктами: `Aetheris.Host` (ASP.NET Core, точка входу), `Aetheris.Core` (спільне: конфігурація, час гри, помилки), модулі-заготовки без логіки: `Economy`, `Planets`, `Fleet`, `Market`, `Rating`, `Chat`, `Admin`; `Aetheris.Tests`.
- Правило: модулі спілкуються лише через публічні інтерфейси (перевірка архітектурним тестом).
- Окрема папка `client/` під React + TypeScript + PixiJS (лише порожній каркас Vite, без екранів).

### 2.2. Бібліотеки сервера
| Призначення | Бібліотека |
|---|---|
| Веб і API | ASP.NET Core |
| Реальний час | SignalR + MessagePack |
| Облікові записи, вхід (email + Google) | ASP.NET Core Identity |
| База (PostgreSQL) | драйвер Npgsql + EF Core (схема, міграції) + Dapper (гарячі запити) |
| Фонові служби / планувальник | `BackgroundService` (заготовка за tech/07) |
| Логи, метрики | Serilog, OpenTelemetry, Sentry |
| Перевірки | FluentValidation |
| Тести | xUnit, FsCheck, WebApplicationFactory (на локальній `aetheris_test`) |

### 2.3. База даних
- ✅ Використовуємо вже розгорнуту локальну **PostgreSQL 17**. Рядок підключення через змінні середовища / локальний файл налаштувань, не в репозиторії.
- Окремі бази на цьому сервері: `aetheris_dev` (розробка) і `aetheris_test` (автотести, очищається між прогонами).
- Початкова міграція: `config_version`, `config_parameter`, `scheduled_event`, `player_event`, `admin_account`, `admin_audit_log` (tech/03).
- Перевірка здоров'я: `GET /health` показує стан сервера й бази.

### 2.4. Конфігурація без хардкоду (✅ жорстке правило)
- Модуль конфігурації: завантаження параметрів з бази в пам'ять, атомарна підміна, перезавантаження після змін.
- Правила гри читають значення лише через цей модуль. Один тестовий параметр (наприклад `test.hello_multiplier`) і автотест: зміна значення в базі змінює результат без зміни коду.
- У CI аналізатор «магічних чисел» (початково як попередження).

### 2.5. Час гри
- Заготовка годинника гри з якорем `(real0, game0, k)` (tech/07, розділ 6), `k = 1`; юніт-тести на зміну `k`.

### 2.6. Запуск
- Одна команда для розробника (наприклад `dotnet run --project Aetheris.Host`): застосовує міграції до локальної бази й запускає сервер.
- `README` з кроками: вимоги, запуск, тести, змінні середовища.

### 2.7. CI
- GitHub Actions: збірка → тести (PostgreSQL 17 піднімається службою GitHub Actions) → перевірка стилю.

## 3. Критерії приймання
1. Одна команда запуску застосовує міграції до локальної PostgreSQL 17 і запускає сервер без ручних кроків.
2. `GET /health` повертає OK і підтверджує з'єднання з базою.
3. Міграції створюють таблиці з tech/03 (у межах переліку п. 2.3).
4. Тест «зміна параметра в базі змінює результат без перезбірки» зелений.
5. Тест на SignalR: клієнт підключається, отримує тестову подію з номером.
6. Архітектурний тест: модулі не звертаються до чужих внутрішніх типів.
7. CI зелений на чистому клоні.
8. Секрети лише у змінних середовища, у репозиторії їх немає.

## 4. Що не входить
Ігрова логіка, екрани клієнта, платежі, адмінка (лише заготовка модуля), розгортання на сервері.
