## 3. Що робимо
1. **Gitleaks:** додати `.gitleaks.toml` (підключається автоматично) з винятком для **шляхів тестів** (`**/tests/**`, `**/__tests__/**`) за правилом `generic-api-key`; щоб не приховати справжній витік, виняток діє лише на ці каталоги й лише на це правило. Перевірити, що CI зелений на історії (скан усієї історії, 6 знахідок зникають), а свідомо доданий тестовий «справжній» ключ поза каталогами тестів все ще ловиться (перевірка вручну, у репозиторій не комітити).
2. **Нестабільний клієнтський тест:** з'ясувати причину (імовірно, гонка між появою заголовка та викликом запиту; очікувати виклик через `waitFor`/`findBy`), виправити так, щоб тест був детермінований; прогнати 50 разів поспіль локально (`--repeat`/цикл) без падінь.
3. **Нестабільний серверний тест:** знайти причину (порядок блокувань при видачі стартової планети, deadlock у `star_system`), виправити код або тест (повторна спроба при `deadlock`/скасуванні в сервісі видачі, якщо це реальний дефект), прогнати 30 разів без падінь; записати результат.
4. **Dependabot-PR:** після п. 1–3 перезапустити CI на кожному PR (rebase на новий `main` командою `@dependabot rebase` або оновлення гілки) і:
   - зелений CI: злити в такому порядку: #1, #2, #3, #6, #5, #4, #7 (по одному, дочекавшись зеленого `main`);
   - червоний через реальну несумісність (наприклад, TypeScript 7 або jsdom 30): не зливати; описати в результаті, що саме ламається, і закрити PR з коментарем «відкладено, причина: …» (Dependabot сам відкриє наступну версію);
   - злиття виконує агент через GitHub CLI/інтерфейс лише після зеленого CI; автор підтверджує порядок у цьому завданні, окремого питання не треба.
5. **Конфігурація Dependabot:** перевірити `.github/dependabot.yml`; згрупувати оновлення (npm: dev-залежності разом; GitHub Actions разом; NuGet уже групою), щоб PR було менше; мажорні оновлення не групувати з мінорними.

## 7. Результат виконання (агент, 28.10.2026)

### Що зроблено
1. **Gitleaks.** У `.gitleaks.toml` додано перевизначення правила `generic-api-key`: воно лишається стандартним (регулярний вираз із типового набору), але має власний allowlist за шляхами `(^|/)tests/` і `(^|/)__tests__/`. Інші правила сканують каталоги тестів як і раніше, а `generic-api-key` сканує решту репозиторію. Загальний allowlist не змінено.
2. **`PlanetPage.test.tsx`.** Причина: заголовок «Планета Nova» береться з акаунта і з'являється до того, як пасивний ефект `usePlanet` викличе `planets.planet`; перевірку виклику робили синхронно одразу після заголовка. Тепер вона чекає виклик через `waitFor`. Прогін 50 разів поспіль: 50/50 зелені.
3. **Серверний тест конкурентності.** Це реальний дефект сервісу, не тесту: у лозі PostgreSQL `40P01 deadlock detected` між двома запитами `SELECT … FROM star_system … FOR UPDATE`. Механізм: у READ COMMITTED запит із `FOR UPDATE` (і навіть із `SKIP LOCKED`) блокує новішу версію рядка, якщо її змінила інша транзакція, перевіряє умову повторно і, коли рядок уже не підходить (система заповнилась), лишає його заблокованим і йде далі. Так виклик тримав одну систему й чекав на іншу, а другий виклик робив навпаки. Виправлення в `StartPlanetAllocator`:
   - кожна спроба взяти тіло в системі йде під точкою збереження; система без вільного тіла й «зайві» блокування, які запит лишив без повернення, відпускаються відкатом до точки збереження;
   - перед очікуванням на блокування системи виклик відпускає все, що встиг заблокувати, і стає в чергу за транзакційним advisory-lock; тож на системи чекає щонайбільше один виклик, і ніхто з тих, на кого він чекає, сам не чекає.
   Базова лінія до виправлення: 2 падіння з 30 (`deadlock detected`). Після: `Parallel_newcomers_never_share_a_body` 30/30 зелені, у лозі PostgreSQL нових deadlock немає.
4. **Dependabot-PR.** Не злито: на машині агента немає GitHub CLI з правами, а виправлення ще не запушено. Чек-лист для автора нижче.
5. **`.github/dependabot.yml`.** Групи: NuGet `microsoft` і `opentelemetry` (мінорні й патчі) та окремо `microsoft-major` і `opentelemetry-major`; npm `npm-development` (dev-залежності, мінорні й патчі), мажорні оновлення npm лишаються по одному PR; GitHub Actions `github-actions` (мінорні й патчі) та `github-actions-major`.

### Перевірки

### Що не перевірено локально
Gitleaks локально не запускався (завантажити бінарний файл на машині агента не дозволено). Перевизначення правила з тим самим `id` за `useDefault = true` зливається з типовим правилом (нові allowlist додаються, регулярний вираз лишається); це треба підтвердити першим запуском CI. Ручна перевірка, яку варто зробити автору (тимчасовий файл не комітити):
```
gitleaks git --redact --verbose --exit-code 1 .          # 0 знахідок
printf 'api_key = "Zx9qL2mN8vB4cR7tY1wE5uI3oP6aS0dF"\n' > leak-check.txt
gitleaks dir --redact --verbose --exit-code 1 leak-check.txt   # 1 знахідка generic-api-key
rm leak-check.txt
```

Особливо перевірити: #3 (`setup-dotnet` 6) серверну задачу й кеш NuGet; #4 (TypeScript 7) `npm run build` (`tsc -b`) і lint; #5 (jsdom 30) клієнтські тести; #7 (Microsoft NuGet) збірку, тести й `dotnet list package --vulnerable`. Червоний через несумісність PR закрити з коментарем «відкладено, причина: …».
