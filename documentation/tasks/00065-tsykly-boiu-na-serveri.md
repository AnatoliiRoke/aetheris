# Задача 00065 — Цикли бою на сервері: розстановка, накази, відрізки, кінець

> **Статус:** чернетка (чекає погодження автора)
> **Запит автора (12.11.2026):** задачі боїв з узгодженої логіки. Ця — повний життєвий цикл бою на сервері та API для клієнта.
> **Логіка бою:** [game-design/06](../game-design/06-kosmichni-boi.md) §3–§5, §8, §9.1.
> **Обов'язково прочитати:** `documentation/tech/08-pravyla-kodu-dlia-ahentiv.md`, `documentation/tech/09-zvedeni-pravyla-kodu-lohiky-ta-kodiv.md`, `documentation/tech/07-planuvalnyk-podii.md`, `documentation/tech/04-api.md`, `documentation/tech/05-bezpeka-ta-antychit.md`.
> **Залежить від:** [00071](00071-boiovyi-poriadok-flotu.md), [00063](00063-rushii-boiu-symuliator.md), [00064](00064-pochatok-boiu-atakuvaty-ta-perekhoplennia.md).

## 1. Як є зараз

Після 00064 бій створено й флоти в стані `in_combat`, але далі нічого не відбувається.

## 2. Рішення

1. **Фази** (06 §3): `deploy` (`combat.deploy_seconds`) → `orders` (`combat.pause_seconds`) → `resolve` (миттєвий розрахунок рушієм) → знову `orders` … → `finished`. Перехід фаз — події планувальника `combat.phase_end` (не опитування).
2. **«Готово»:** якщо всі сторони з живими гравцями (або офлайн-сценарієм) підтвердили, фаза закінчується одразу (перепланування події).
2а. **Розподіл спільного трюму** (06 §7.4): при вході флоту в бій (на початку бою й для підкріплення) сервер розкладає спершу за бажаним розподілом із формації (00071), а решту `fleet_cargo` і деталі трюму (дрони, боєприпаси) по кораблях через `HoldSplitter` (00063) і зберігає розподіл у стані бою. У фазі `deploy` гравець може змінити розподіл (`POST /combat/{id}/hold`) у межах місткості кожного корабля; підкріплення, що входить пізніше, отримує лише автоматичний розподіл.
3. **Ескадрильї:** при створенні бою беруться з **типової формації флоту** (задача [00071](00071-boiovyi-poriadok-flotu.md)): склад, поведінка, розстановка, бажаний розподіл трюму. У фазі `deploy` гравець одним запитом **перемикається на іншу формацію** флоту (`POST /combat/{id}/formation`, перераховується склад ескадрилей, розстановка й розподіл трюму); за бажанням ділить, об'єднує й підправляє ескадрильї у фазах `deploy` і `orders`. Без втручання бій стартує з типової формації. Перемикання поза `deploy` відхиляється.
4. **Накази** (06 §4): маршрут (точки), поведінка, правило пріоритету, ціль фокусу (лише видима), дрони (запустити/відкликати), розстановка (лише в `deploy`, лише в своїй зоні). Накази таємні до розрахунку. Без нових наказів діють попередні.
5. **Розрахунок відрізку:** рушій 00063 з `combat.segment_seconds`; результат — новий стан (зберігається) і результат відрізку (сліди руху, журнал — для екрана й звіту). Одна транзакція на розрахунок; блокування бою від паралельного розрахунку.
6. **Видимість у відповідях** (06 §5, античит tech/05): клієнт отримує лише те, що його сторона бачить; позиції й склад невидимих ворогів сервер не віддає, і сліди та журнал фільтруються так само (слід ворожої ескадрильї — лише та частина, яку сторона бачила).
7. **Підкріплення** (06 §9.1): флот, що прибув до точки бою з наказом атаки або ставкою (своєї чи ворожої сторони), входить на початку наступного циклу з краю поля, з якого підлетів.
8. **Кінець бою** (06 §8): на полі лишилась одна сторона, або досягнуто `combat.max_cycles` (нападник відходить). Ескадрильї, що вийшли за край, повертаються у світ флотами поруч із місцем бою; їхні листи знімаються з паузи. Наслідки — 00066.
9. **Офлайн:** якщо гравець не дав наказів, діють попередні або сценарій 00067 (до 00067 — шаблон «стояти й стріляти за найближчими»).
10. **Сповіщення клієнта** про зміну фази й новий відрізок — через наявний канал реального часу (той самий, що для подій гри); якщо його немає для бою, додати повідомлення в нього, без опитування клієнтом.

## 3. Що зробити

1. Таблиці Combat: `combat_squadron` (сторона, флот, склад кораблів), `combat_order` (цикл, ескадрилья, наказ JSON), `combat_state` (стан після циклу, стиснутий), `combat_segment_log` (цикл, журнал, стиснутий), `combat_ready`.
2. Сервіс фаз і обробник `combat.phase_end`; розрахунок через `SegmentSimulator`; збереження стану.
3. API (за tech/04): `GET /combat/{id}` (стан для своєї сторони, фаза, таймер), `POST /combat/{id}/squadrons` (розділити/об'єднати), `POST /combat/{id}/orders`, `POST /combat/{id}/ready`, `GET /combat/{id}/segments/{cycle}` (результат циклу: сліди руху й журнал, відфільтровані), `GET /combat/active` (бої гравця). Перевірка прав: лише учасник бачить і керує своєю стороною.
4. Підкріплення: точка входу з напрямку підльоту.
5. Тести: повний бій від створення до кінця; «Готово» скорочує фазу; накази поза зоною розстановки відхиляються; ціль фокусу невидима — відхилено; автоматичний розподіл трюму і його зміна в `deploy` (понад місткість — відхилено, поза `deploy` — відхилено); фільтр видимості у відповідях і журналі; підкріплення входить з правильного краю; ліміт циклів; вихід за край повертає флот у світ.

## 4. Критерії приймання

1. Бій проходить усі фази без участі адміністратора; таймери — події планувальника.
2. Клієнт не може отримати дані про невидимих ворогів (тест на API).
3. Розрахунок відрізку детермінований і повторюється з тим самим результатом зі збереженого стану.
4. Усі перевірки зелені.
