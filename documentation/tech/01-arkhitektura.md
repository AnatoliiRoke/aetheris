## 2. Загальна схема (💡)

```
 Браузер (клієнт)                 Сервер
 ┌──────────────┐   HTTPS/JSON   ┌──────────────────────────────────┐
 │ Інтерфейс    │ ─────────────► │ API (команди гравця, запити)     │
 │ 2D-карта,    │ ◄───────────── │                                  │
 │ бій          │   WebSocket    │ Ігрове ядро (правила, формули)   │
 └──────────────┘  (події)       │                                  │
                                 │ Планувальник подій (таймери)     │
                                 │ Обробник боїв                    │
                                 └───────────┬──────────────────────┘
                                             │
                               ┌─────────────┴────────────┐
                               │ База даних  │  Кеш / черги│
                               └──────────────────────────┘
```

- **Клієнт нічого не вирішує**: лише показує стан і надсилає команди («збудуй шахту», «відправ флот»). Усі перевірки й розрахунки на сервері (✅ важливо для античиту, документ 05).
- ✅ **Модульний моноліт**: один серверний застосунок, поділений на модулі (економіка, планети, флот, бій, ринок, клани, рейтинг). Для одного розробника це простіше за мікросервіси; модулі можна винести окремо пізніше.

## 3. Як працюють таймери в реальному часі (💡)

Головна технічна задача: мільйони таймерів (будівлі, дослідження, флоти) без постійного перерахунку всього світу.

### 3.1. Ресурси: «ліниве» обчислення
- Сервер **не додає ресурси щосекунди**. Для планети зберігається: кількість на момент `T`, швидкість видобутку, ліміт сховища.
- Поточна кількість рахується за формулою, коли потрібна: `зараз = min(ліміт, кількість_T + швидкість × (зараз − T))`.
- Коли щось змінює швидкість (нова шахта, грабунок), сервер фіксує новий `T`.
- Так само для населення (приріст до максимуму).

### 3.2. Події: черга запланованих подій
- Кожна дія з тривалістю створює **подію** з часом завершення: «будівля X готова о 18:42», «флот прибуде о 19:10».
- **Планувальник** бере події, час яких настав, і виконує їх по черзі.
- Події обробляються **строго за часом**: якщо флот прибуває о 19:10, а щит планети закінчується о 19:09, спершу закінчується щит.
- 💡 Події зберігаються в базі даних (не губляться при перезапуску сервера).
- 💡 Докладний опис планувальника: [07 — Планувальник подій](07-planuvalnyk-podii.md).

### 3.3. Бій
- Початок бою — подія (флот прибув до цілі).
- Кожен цикл — теж подія через 5–10 хв; між ними гравці надсилають накази.
- Розрахунок циклу — детермінований (одні й ті самі дані → той самий результат), з **зерном випадковості**, записаним у звіт. Це дає змогу відтворити бій для анімації і перевірки.

### 3.4. Швидкодія сервера (💡)

✅ Вимога автора: **сервери мають працювати швидко.** Гра не потребує оновлень 60 разів на секунду, тому швидкість визначає насамперед архітектура. Принципи нижче не залежать від мови програмування (документ 02).

1. **Гарячий стан у пам'яті.** Активні об'єкти (планети онлайн-гравців, флоти в польоті, бої, ринкові книги заявок) живуть у пам'яті сервера. Читання стану не звертається до бази даних.
2. **Запис у базу пакетами.** Зміни накопичуються і записуються в PostgreSQL кожні 1–2 секунди однією транзакцією. Критичні дії (оплата, грабунок, торгівля) записуються відразу.
3. **Таймери в пам'яті.** Планувальник тримає найближчі події в черзі за часом (купа / heap) і «спить» до наступної. Копія подій зберігається в базі; після перезапуску черга відновлюється з бази.
4. **Ліниві ресурси** (розділ 3.1): жодного щосекундного перерахунку.
5. **Один власник на сектор.** Кожен сектор обробляє один потік / процес. Події в секторі виконуються по черзі без блокувань; так легше уникнути помилок одночасного доступу і пізніше розділити навантаження (розділ 4).
6. **WebSocket надсилає лише зміни** (дельти), а не весь стан; клієнт підписується лише на те, що бачить (свою планету, свій бій, видимий сектор).
7. **Довідники балансу** завантажуються в пам'ять під час старту, а не читаються з бази на кожен запит.
8. **Бій** рахується на сервері один раз за цикл; клієнт отримує готовий звіт і лише програє анімацію.
9. **Вимірювання з першого дня:** час обробки запиту, довжина черги подій, час розрахунку циклу бою. Ціль: 95% запитів швидше за 50 мс.

### 3.5. Повільна мережа (💡)
- Кожна подія для клієнта має **зростаючий номер**. Після обриву клієнт просить події з останнього отриманого номера; сервер надсилає лише пропущене (або свіжий знімок, якщо пропусків забагато).
- Клієнт показує очікуваний результат дії одразу, сервер підтверджує пізніше.
- Повідомлення бінарні й компактні (дельти); докладно в документі 02, розділ 5.

## 5. Надійність (💡)

- Резервні копії бази даних щодня, зберігання 14–30 днів.
- Кожна зміна стану — у **транзакції** (наприклад, грабунок: мінус у жертви і плюс у нападника разом).
- Журнал дій гравця (для підтримки і розслідувань).
- Плановий перезапуск без втрати подій.

### 5.1. Розгортання, копії, моніторинг (✅ попередньо підтверджено автором, 24.10.2026)
- **Розгортання:** Docker на одному VPS Hetzner (застосунок, PostgreSQL, Redis за потреби); автоматичні збірка і тести (CI на GitHub); оновлення однією командою, нова версія запускається поруч зі старою. Короткі планові перерви (1–2 хв) прийнятні, таймери не губляться (події в базі).
- **Копії:** щоденна повна копія бази + безперервне архівування журналу змін (WAL) для відновлення на будь-яку мить; зберігання в іншому місці (Hetzner Storage Box або Cloudflare R2), 14–30 днів; щомісячна перевірка, що копію можна відновити.
- **Моніторинг:** метрики (час відповіді, довжина черги подій, час розрахунку бою, пам'ять, диск, помилки), Sentry, Grafana; сповіщення в Telegram/пошту при падінні, заповненому диску, зростанні черги.
- **Резервний сервер на старті не робимо** (попередньо ✅): копії + швидке відновлення (година-дві простою). Додаємо, коли гравців стане багато.
- **Страховий знімок** гарячого стану в базу кожні 10–15 хв (💡); критичні дії пишуться в базу відразу.

## 8. Відкриті питання

1. ✅ **Модульний моноліт** замість мікросервісів (підтверджено автором, 24.10.2026). Правило: модулі спілкуються лише через публічні інтерфейси, без прямого доступу до чужих таблиць. Адмін-ендпоінти довідника належать модулю-власнику (задача 00023): модуль описує вид, тримає таблиці й сервіс і сам відображає свої маршрути (`/admin/planets/...`, `/admin/research/...`) на захищену групу адмінки, яку дає Host; Host лише підключає групу, збирає описи видів для меню й додає коди дій у сид дозволів. Спільний лише протокол у `Aetheris.Core/Admin`, спільної таблиці довідників немає.
2. ✅ **Коефіцієнт часу** в адмінці (підтверджено автором, 24.10.2026); окремий тестовий сервер на старті не обов'язковий. 💡 Весь час гри береться з одного «годинника гри» з множником (на бойовому сервері за замовчуванням 1); зміна множника записується в журнал адмінки. Оскільки `run_at` зберігається в ігровому часі, зміна множника **прискорює (чи уповільнює) і вже запущені таймери** без перерахунку, а ресурси рахуються за ігровим часом; докладно в документі 07, розділ 6 (документ 05, розділ 8).
3. ✅ **Розподіл за секторами** (підтверджено автором, 24.10.2026). Спочатку нарощуємо потужність одного сервера (пам'ять, процесор). 💡 Логічний поділ за секторами закладаємо з першого дня: кожна подія й об'єкт має сектор-власника, модулі не звертаються до даних чужих секторів напряму, міжсекторні дії йдуть повідомленнями. На старті всі сектори обробляє один процес; фізичний поділ на кілька процесів потім стане налаштуванням, а не переписуванням.
